# HobbyKit — Agent Guide

Read [README.md](README.md) first for what the app does and what the controls mean, then [CONTRIBUTING.md](CONTRIBUTING.md) for setup and layout. This file covers the parts that bite.

This application is built from RAS recipes. `ras-recipes.json` records each recipe it took, the version and commit it came from, where the recipe's files live here, and every intentional difference from the recipe. Add, update, or check recipes with the `ras-recipes` skill in [ras-stack](https://github.com/richardsolomou/ras-stack/tree/main/skills/ras-recipes), and record each new intentional difference in that recipe's `notes`.

## Commands

- `just check` — the local gate: format, lint, typecheck, unit tests, build. Run it before pushing.
- `just dev` — Vite on port 5173.
- `just test` — Vitest over `src/**/*.test.ts`. Geometry tests run in Node against the same builder the browser uses, so they need no browser.
- `just e2e` builds and runs Playwright; `just e2e-run` reuses the current `dist/`. Install the browser once with `just e2e-install`.
- `just social-cards` — rebuilds and retakes every page's link preview image in `public/og`, the README screenshots and the GitHub social preview in `docs/images`. The social preview is uploaded by hand under the repository's Settings → Social preview.
- `just makerworld-images [name...]` — rebuilds and renders MakerWorld listing images into `makerworld/images`, which git ignores: 4:3 and 3:4 covers, a grid of other configurations, and a plain render. Every configuration shown must be one the MakerWorld script can make, because MakerWorld treats a render the download cannot produce as misleading, and each listing still needs a photo of a real print.
- `just printables` — writes the ready-to-print STLs and `.scad` for each Printables listing into the git-ignored `printables/files/<name>/`; the copy in `printables/listings` names every file, so change both together.
- `just samples [round|oval|painting|rack|counter]` — writes preset base STLs, the default painting tray, the default paint rack, or the default dial counter's parts and inserts for inspection outside the browser.
- `just makerworld` regenerates the generated tables in every `makerworld/*.scad`; `just makerworld check [name[/case]]` renders each script's cases from `scripts/makerworld/<name>.ts` with OpenSCAD and compares them against the app.
- Lint and format are oxlint + oxfmt, not ESLint/Prettier. Warnings are denied in CI.

## Load-bearing rules

- **The part is modelled the way it prints, not the way it is used.** `z = 0` is the face the model is glued to and sits on the build plate; `z = height` is the base's underside, the face that meets a magnetised tray, and it is the top of the model as built. That is what keeps every overhang pointing up so nothing needs supports, and it is why the app opens looking at the underside. Get this backwards and every conclusion about magnets inverts: bores open at `z = height`, and `floorThickness` is nowhere near a magnet. Relief textures are the one exception, below.
- **The recess exists to hold magnets**, so the model holds itself down on a magnetised surface. Nothing is basing material, there is no topper, and no filler flows anywhere. Earlier versions of these docs claimed otherwise.
- **`src/core/geometry` stays DOM-free.** It runs in a worker, in Node tests and in the samples script. No `window`, no `document`, no fetch. Fonts and the WASM module are passed in by the caller.
- **Every Manifold object must be handed to `own()`** in `buildBase`. WASM memory is not garbage collected, and the `finally` block is the only thing freeing it. Chained calls create intermediates — each one needs owning.
- **The body loft assumes a convex footprint.** It is built as the convex hull of the outline offset at each height of the edge profile, which is exact for circles, ovals, pills, rects and polygons. A concave shape would need a real loft instead.
- **Never leave two surfaces exactly tangent.** Ribs deliberately run 0.4mm into the wall: stopping them flush left a single shared point, which stayed manifold in Manifold's own topology but pinched into a non-manifold edge in any tool that welds vertices by position, slicers included. `base.test.ts` asserts no two vertices share a position.
- **Guard on real geometry, not bounding boxes.** A triangle's inradius is far under its bounding box, so a width-based wall check passed configs whose well offset away to nothing; the infinite bounds that came back sent rib placement into an allocation loop. Check `CrossSection.isEmpty()` instead.
- **Oval row reach follows the curved well, not its bounds.** A boss that clears the end of the well's bounding box can still cut through the ellipse above and below its centre. `magnetPositions` uses a conservative ellipse reach for oval rows; pills and rectangles keep their farther flat/circular-cap reach.
- **The edge profile must leave wall beside the recess floor.** The well is cut from the full-size inner outline while the outer loft is inset near the build plate. If that inset reaches the well outline where the floor begins, the cut severs the rim and only the ribs join it back. `maxProfileSize` samples the same profile steps as the loft, the UI caps against it, and `buildBase` rejects callers that bypass the control.
- **Every magnet boss sits on a rib.** That is the invariant `base.test.ts` asserts across every preset, and the counts are chosen to hold it: a ring gets one spoke each, and a row gets an even count, because every magnet in a row shares the long axis so one spoke down it passes through all of them. `ribAngles` takes its phase from a boss bearing so the alignment is exact. It used to fall out of both series using the same `π/2 + 2πi/n`, which meant it held only when the counts happened to match, and flipped as the size changed. A rib on a boss gussets its root, prints as one connected feature instead of an island, and collects the clear floor into a few wide gaps, which is what lets the size label stay large. Phase makes almost no difference to floor stiffness — a boss is a 7mm inclusion in a plate tens of millimetres across.
- **Automatic magnet counts combine holding demand with stability.** `automaticMagnetCount` starts from the existing 5×2mm balanced recommendation, scales demand by the practical `diameter² × thickness` strength proxy, applies a minimum of three magnets for a ring or two for a row, then rounds up to a supported balanced count. This assumes ordinary neodymium magnets; it is a recommendation, not a pull-force claim. A `magnetCounts` entry is a per-footprint manual override, while an absent entry means automatic. Every automatic count must appear in `MAGNET_CHOICES` and every rib count in `RIB_CHOICES`; tests assert both.
- **Label bearings come from the gaps between everything solid**, ribs and bosses together, widest first. Bisecting the ribs alone worked only while ribs and bosses shared a bearing; the moment they did not, a rib bisector aimed straight at a boss. Bases and holders both use `src/core/geometry/label.ts`, so changes to fitting rules affect both generators. Equally wide gaps go nearest −y, then toward −x, compared at 1e-9 so float noise never picks one: OpenSCAD's noise differs from JavaScript's, and the MakerWorld port must land on the same gap.
- **The size label must never disappear silently.** If it cannot be placed it is simply absent from the model, with no error, so changes to `fitLabel` need a test that a cramped base still gains volume from its label. Custom label text is different: someone typed it, so text that cannot be placed throws and blocks the build instead. The input accepts only `LABEL_CHARACTERS`, which a test checks against the bundled Oswald, up to `LABEL_MAX_LENGTH`. The text is base-only and survives size changes; filenames always name the size, never the label.
- **Textures are cut into the plate face, so every joint is a 45° V.** `textureCells` lays out every pattern as convex anticlockwise cells: flagstones, cobbles and hex tiles are Voronoi cells of a jittered lattice (cobbles then have their corners rounded), herringbone is a staircase of flat and upright bricks turned 45°, and square tiles, planks, plates and diamonds are rows along the longer axis. `textureCut` builds each stone from its whole cell, trimmed by one 45° plane per edge, and subtracts the stones from a slab reaching past the wall, so joints run out through the edge and the pattern reaches the lip. A plain border with a joint round it was tried first and rejected: the pattern looked as if it stopped short. Hulling the cell's insets at two heights was tried first and left 40° faces wherever a short Voronoi edge vanished partway down. Neighbouring stones stop `APEX` short of each other at the top, leaving a 0.02mm flat along every joint's apex rather than a shared edge; `texture.test.ts` allows that flat and nothing else. A heightmap cannot go on that face: a gentle slope on a face that prints against the plate is a near-flat ceiling. Joint depth is capped at `floorThickness - MIN_TEXTURE_FLOOR`, `resized` and the panel clamp it as the floor changes, and `buildBase` rejects callers that bypass them.
- **Every pattern has a variation and most have an irregularity.** `seeded` offsets the shared hash by `seed`, so a base rerolls without changing anything else, and `irregularity` (0–100) widens whatever makes a pattern untidy: Voronoi jitter, plank lengths, row offsets, slab tilt, stone sizes. Herringbone and diamond plate are regular (`isRegular`) and the panel hides both controls for them. `withPattern` carries any value the user changed across a pattern switch and takes the new pattern's defaults for the rest.
- **The preview shows a joint-textured base turned over.** Joint patterns print face down, so as built the texture faces away from the default camera. `Viewer` takes `flipped` and turns the part a half turn about X within its own height; exports and the mesh stay as built. Relief bases print face up and need no flip.
- **Relief textures turn the base over.** Rock, earth and rubble (`isRelief`) build the body solid with `z = 0` as the face that meets the tray and the model face on top, because a heightfield printed face up has no overhang anywhere. The edge profile is mirrored so the full-size face still meets the tray. Pockets open at `z = 0`, so magnets stay flush with the tray face and only their 5.2mm ceilings bridge; `MIN_POCKET_ROOF` keeps material above them. There is no well, ribs or floor, and the size label is engraved into the underside, mirrored so it reads from below. Magnet positions still come from the wall-inset outline, so trays match either orientation. `reliefBlock` samples a procedural surface of `scale`-sized features on a regular grid, blurs the heights by `SOFTEN`, builds the grid as a closed heightfield lifted `LIFT` clear of the body's top face, and intersects it with the model face inset `EDGE` inside the lip, so neither its walls nor its surface meets the body's top edge. The blur is what keeps every pattern smooth: surfaces are free to have cliffs and fine noise, and sampled raw those exported as saw teeth along every wall. Warping a refined slab instead streaked the surface, because refining a polygon's triangulation keeps its long radial slivers. The grid is offset by a fraction of a cell so no grid line lands on a rectangle's straight edge, which left coincident vertices. Extending the hull upward instead does not work: a convex hull smooths away the crease between a taper and a vertical wall above it. Surfaces stretch their noise linearly; easing it saturated whole regions into flat plateaus that printed as relief cut off a layer or two down. The grid is 0.25mm on export and previews coarsen with size to 0.8mm by 100mm, chosen from the curve tolerance; a 100mm export takes about 2.5s. `relief.test.ts` asserts the only downward faces are the pocket and label ceilings, and that no relief face is steeper than 65° even at the smallest, roughest setting.
- **Magnets are flush with the face that meets the tray, whatever their thickness.** The bore is cut down from `z = height` by `magnets.thickness + magnets.depthClearance`, leaving optional room for adhesive behind a magnet held flush during assembly. Anchoring the bore at `floorThickness` instead looks like it puts the magnet "on the floor", but that floor is the opposite face of the base, so it strands the magnet as far from the tray as the geometry allows. `base.test.ts` asserts the bore's ceiling is `z = height` at every thickness.
- **Holder modules are built from the layout the plan found, never planned again.** `relaxedPacking` can fit more slots than `maxPossibleGroupQuantity` estimates for the box it lands in, so planning a module again within its own size, which the export once did, came out with fewer slots than the preview. The export passes the whole config with a `module` index, the way a paint rack passes `piece`. Slots also stop at least `MIN_EDGE_SPACING` inside the wall whatever the edge spacing: at zero a hex corner or a round slot's polygon vertex touched the wall and welded into open edges.
- **Painting trays are interleaved magnet grids, not miniature holders.** Rows and columns define the primary pockets, with one offset pocket at the centre of every four adjacent positions. The diagonal pockets give mixed base sizes more placement options; do not pack miniature footprints or add surrounding recesses.
- **The painting-tray handle is a separate configurable glue-on grip.** Round, oval-barrel, flared, and pistol shapes can vary in width, length, lean, end softening, and ribs while staying upright and support-free. Its flat end meets the tray underside directly, without a mounting plate. Keep the grip free of integrated finger shields or guard flanges; that approach obscures the clean grip and was rejected. STL export puts tray and handle in a ZIP and 3MF export gives each part its own build plate. Do not export the grip fused to the tray: a handle extending beneath the tray cannot print support-free in the tray's orientation.
- **Paint racks are hollow cells under thin decks, never solid steps.** Each bottle gets a hex cell whose walls are shared with its neighbours and stand on the plate. Default walls are 0.85mm, two nozzle lines that slice as plain perimeters; 1.2mm walls added slow gap fill and about 1h25m to a 5×4. What a rack looks like comes from its top surfaces, and every one of them costs print time, so each is as thin as it can be. A 0.8mm deck caps each cell, bridged between the walls and a bore tube, which stands on a 45° funnel whose upper face is the dropper ledge. The tube, funnel and ledge are one revolved profile, and the tube tops out inside the deck, whose hole is half a wall wider, so no two faces coincide. Above the deck the pot pocket is the hex cell itself, rounded only by a 0.8mm rim whose underside chamfers out to the walls at 45°. A thin round pocket wall with hollow corners merged with the hex walls into 1.5mm strips of gap fill and printed slower than solid corners. The air sealed under each deck decomposes as a negative-volume body, which is expected. Decks bridge to their bore instead of resting on 45° wedges, so slicers with auto supports on will support them; wedges made the rack support-free under any setting but added 52 minutes to a 5×4. A dropper is held only by its bore below the deck, since the pocket is far wider than the bottle, while a pot is held only by its pocket, so the two depths are independent. Defaults pair a 5mm pocket, low enough to read a Citadel label and still hold the pot, with a 16mm seat under a 17mm front deck; an 8mm seat let Vallejo droppers lean about 10° and wobble. On a 5×4 on the X2D at 0.20mm Standard with supports off, that rack slices to about 4h53m and flat decks to about 4h02m, against 5h44m for the solid original and 2h55m for open cells with no decks, which looked like an empty crate and was rejected. Seats reach the middle of the walls rather than stopping at their faces. A funnel that would reach the plate before the walls' corners lands on a floor instead of floating. A loadout is printed as separate pieces: modules in order with optional ends, each built alone through `piece` for export and side by side for the preview. Every module shares one lattice, front-aligned with odd rows half a cell right, so neighbouring zigzag edges interlock. Pieces stand apart along a run by twice the wall plus `PIECE_CLEARANCE`, because the slanted walls face 60° off the row and a sideways shift opens them by only half of itself. An end adds lattice cells beside the first or last piece, one more per row for every two rows back, so the side steps back at the lattice's own 60°. A corner turns the next run a quarter clockwise round an inside corner: a square as deep as the run, split by a 45° mitre from the inner corner to the wall corner, with this run's lattice on one side and the next run's, turned, on the other. Each half's cells reach a wall past the mitre and are hollowed only to the mitre wall's face, so the band between them is solid with no coincident faces. A cut cell keeps its seat when its pocket clears the mitre, is capped at its rim and packed with `brushDiameter` tubes when it is still `MIN_CUP` wide, and is filled solid when it is only a sliver. Open wells there were rejected as wasted space. Brush holes default to 10mm, the smallest a printed fit gauge showed Army Painter's triangular grips passing; common round holders are too tight for them. Pockets default to Ø33.3 in 35mm cells: a printed test cell at Ø33.2 held Citadel pots whose label wrap overlaps at the seam, and the extra 0.1mm leaves a little play. A 6mm-tall gauge ring needed Ø34.5 for the same pots, because the pocket grips only at its thin rim and opens out below; size pockets from a test cell, not a ring. A pocket must stay `POCKET_CLEARANCE` inside its cell's walls; Ø34.5 in a 35.5mm cell left 0.075mm of rim at the flats, which printed as a sliver. Brush tubes stand as separate rings that start narrower than their hole, and the holes are drilled after everything else is joined, so the hole is the only face at that radius; carving the tubes out of the cell's hollow instead left pinched vertices where the mitre wall met the hex walls. Every piece is a list of cells in its run's frame, built through one path. A rack grows over time from either end, so `items` is an ordered list the panel adds to on both sides, and adding a piece must never change one already printed; a model that split wall lengths into pieces was rejected because lengthening a wall re-split the pieces already on the shelf. Each piece downloads on its own. The preview lays the run with the most columns across the back, so a new corner does not spin the rack. Items all share one shape, with corners ignoring `columns`, because workspace validation checks every array entry against the first, and every piece shares the rack's rows. `paintRack.test.ts` asserts, for every piece, no overhang beyond 45° except the deck bridges, one solid body and no shared vertex positions, and that the assembly's volume is exactly its pieces'.
- **Tokens print face-up, the opposite of bases.** `z = 0` is the table face on the build plate and positive relief raises text and images from `z = thickness`, while negative relief engraves them down from that face, leaving at least 1mm of material beneath the artwork. Zero relief leaves a plain body. Raised artwork is always returned as `inserts`, never joined to the body; it starts exactly at `z = thickness`, so the 3MF gives it filament 2 as a second part with no layer shared with the body, the same as the counter tiles. A one-colour print sets both colours alike, which is why there is no toggle. Engraved artwork stays in the body. Engraving never changes `tokenHeight`; only raised artwork adds to the body thickness. The edge treatment sits on the top edge. Text wraps onto whichever line break gives the largest cap height up to the requested one, and text that would fall below `MIN_TOKEN_TEXT_HEIGHT` blocks the build rather than shrinking into something unprintable. With both an image and text, the image takes the band above `IMAGE_TEXT_SPLIT` and the text the band below.
- **Dial counters are two ten-sided dials that click on spring arms, in one of four layouts, modelled as used and laid flat per part.** The proportions began as a personal remake of a downloaded model under a Standard Digital File License, so **do not publish this design until it has been changed**; never use that model's mesh, logo or art. Full size, 39.6mm, is the default, and 18mm is the smallest, the same part at 0.45 scale: below it the arm cavity would reach the face pockets. Everything above it scales uniformly: `atBaseSize` divides the fits by the scale, the part is built at the base design and then scaled, so clearances, press fits and tile fits stay real distances. **Every click is two spring arms gripping a lobed profile from both sides.** Each arm is a curved strip left between a bore and a crescent cut behind it, spanning 72° with a round bulb at its tip in a trough between the lobes; two arms opposite each other centre what they grip with no play. `click` is the trough depth, and `maximumCounterClick` keeps some of the room behind the arm when a crest passes under the bulb. **`layout` picks what holds the dials.** `enclosure`, the default, puts them in a ten-sided case with a window over the top row, so only the count shows and no bracket is needed; the case is two halves split in the middle, each an end wall and half the shell, printed on its end wall so the window opens upwards, and the left half's inner wall runs on as a lip into a step in the right half's. Inside the case the dials have no end bands, so the case only clears their corners, and the window's long edges are bevelled at 45° so the wall hides none of the number; a thicker case with bands sat 4.3mm above the digits at full size and was hard to read. `knobs` is the same mechanism with open ten-sided hubs the size of the dials, which the counter stands on. In both, the spring arms are cut in the end wall or hub, and each dial runs on as a lobed shaft through it to a ribbed knob pressed on outside, so you turn knobs, never dials; the dials are solid round a bore for a rod, which is part of the left knob, prints standing up from it, and turns with the tens. A dial with a shaft prints on its inner end, so both its end bands are chamfered. The shaft has to stand on solid dial outside the arm cavities if the arms are in the dial, which is why the arms moved into the hubs. `hubs` keeps the arms in the dials, clicking on a fixed fluted tube that is part of the left hub, printed standing up from its outer face, and presses into a lobed socket round a boss in the right hub; each hub is a disc on two legs. `centre` ("Frame and base") holds the tube in a cage: a black frame over the top row stands on a post past each dial, whose legs straddle two flats on each tube end so it cannot turn and plug into a base plate under the dials, which has a cradle under each tube end; nothing sits between the digits. A centre stand between the dials, side pieces, end caps, a frame clipped to a stand and a tube collar inside each dial were all tried and dropped. **`grip` lengthens each dial at its outer end, and its pockets and tiles with it, so a tile and the lines above and below its digit run the dial's whole length.** A dial has no corner ribs: in the second filament they cost a filament change on every layer, and in the body's they cut across the lines that frame each digit. Its corners are bevelled `CORNER_BEVEL` along each face instead, which also keeps the inner band's 45° chamfer from crossing a corner edge at a single point. **The top row is marked by a bracket inlaid flush in each hub, or by the frame or the window.** A bracket is a part of its own, pressing into a slot open above and through both faces with `BRACKET_FIT` of play, deep enough to show on both faces; its hidden foot, `COUNTER_TILE_BASE` high, takes the body's filament and the rest the second, and the 3MF puts both brackets on the tile plate, so that plate changes filament once at the height the tiles do and no body ever does. `digits` picks press-in tiles, the default, `printed` digits or `engraved` ones. Printed digits are a part of the dial a pocket deep and cost a filament swap on every layer; as the default they took far longer to print than tiles, and a third colour, which shares the second nozzle, flushed on every layer too. Digit-shaped inserts were too small to stay on the build plate. `digitFilament` puts tile marks or printed digits in filament 2 by default, returned in `inserts`, or in filament 3, returned in `third`. Each face has a rectangular pocket with barrel left on all four sides, which grips a tile without glue. Each tile is that rectangle shrunk by `insertClearance`, `COUNTER_TILE_BASE` thick, with its digit and the `DIGIT_LINE` above and below it raised so they end flush with the face. Engraved digits are `COUNTER_ENGRAVING` deep. The tiles are their own part, laid face up by `counterTileLayout` in a row of 0–9 per wheel, each built as a base and its raised mark starting exactly at `COUNTER_TILE_BASE`; the 3MF gives every tile an object of its own, named by wheel and digit and built alone through `tile`, so someone reprinting a few deletes the rest. `counter.test.ts` asserts, for every layout and part, one body apart from the tiles, no overhang beyond 45° except pocket and socket ceilings, no shared vertex positions, tiles and brackets that never overlap the bodies, and that the assembly's volume is its parts' less only where bulbs grip. `makerworld/counter.scad` still ports an earlier side-piece design and must be rewritten before the listing is updated.
- **Token sizes are measured across the flats; base hex sizes are not.** A token's `size` is a round's diameter, a square's side, and a hex's flat-to-flat distance, because that is what a hex grid or a ruler laid edge to edge measures. Hex bases stay across-corners so they drop into the space of the matching round. Hex tokens sit flat edge up so text gets the widest band, and the dimension leaders show the real across-corners × across-flats extents. Text and image fitting test each rectangle against the inset face outline's width at its top and bottom edges, which is exact only because every face is convex and mirrored about the y axis — never fit against the bounding box, whose corners overhang a round or hex face.
- **Token images are silhouettes, never heightmaps.** `loadTokenImage` downsamples an upload to a 256px greyscale grid composited over white, and only that grid is saved in the workspace. `traceSilhouette` turns it into even-odd loops with marching squares, and `buildToken` opens the result by the nozzle width so no sub-0.4mm sliver reaches the slicer. The finished face is simplified before extrusion: offsetting can leave coincident points that pinch into non-manifold edges once vertices are welded.
- **Text fills non-zero; traced images fill even-odd.** Oswald's glyphs overlap their neighbours (`ÏÏ`, `fï`, `gj`), and an even-odd fill cuts every overlap out as a hole, so every text section is built with `GLYPH_FILL` from `src/core/geometry/text.ts`. Image silhouettes keep `'EvenOdd'`, because `traceSilhouette` promises nothing about winding.
- **Standard sizes come from published base guides, not memory.** Rounds and ovals follow GW's Warhammer 40,000 Base Size Guide in the Warhammer Event Companion and the Age of Sigmar Battle Profiles, both on Warhammer Community's downloads pages; rectangles follow The Old World's published sizes and Kings of War's unit types. Each `use` names a few units that stand on that base. GW's two guides measure the same ovals differently (40k 60×35.5 and 90×52.5, AoS 60×35 and 90×52), so presets take the 40k figures, and AoS's 170×105 stays separate from the Knights' 170×109. No GW game uses pills, so pill presets stand in for its ovals. Tests and scripts pick presets with `standardSize(shape, label)`, never by index, so reordering a list cannot change what they test.
- **Sizes are exact.** A 28.5mm base reads `28.5` everywhere — size label, footer, filename. Never round a size for display; `trimNumber` drops trailing zeros without rounding.
- **Exports always use a 1µm chord tolerance for circular geometry.** `exportSegmentsFor` derives the segment count from the diameter and round edge profiles inherit the tolerance implied by that count. The preview deliberately uses `previewSegmentsFor` and a lighter mesh; `buildMesh` runs an isolated high-quality build when either export button is pressed. Do not restore a quality control or a fixed export segment count: either makes exported tolerance depend on the size again.
- **A size-driven setting follows the footprint until someone sets it.** Base height, top thickness, corner radius, label size and support count each have a default that depends on the footprint (`sizeDefaults`), and the counter's click one that depends on the wheel (`automaticCounterClick`). Each config's `pinned` lists the ones set by hand; `fitToSize` and `fittedCounter`, run by `synchronizeWorkspace` after every change, recompute the rest, and keep a pinned one only as far as the footprint allows. Every way of changing a footprint, picking a standard size, typing one, changing shape or building a batch entry, goes through `resized`, so all of them keep every style choice (edge, texture, wall, sides, label text) and refit only what follows the size. A control for one of these takes the current size's value as its `defaultValue` and shows `auto` while it follows: setting it pins it, and setting it back to what the size gives, which is what its reset does, lets it follow again. A picked standard size used to load that whole preset, which threw away the edge and everything else, and the highlight compared against the 32mm default, so a value the size had changed looked like an edit and its reset was wrong for the size on screen. Magnet counts work the same way through `shared.magnetCounts`, keyed by footprint so holders and batches share them.
- **Batch entries differ from the current base only in footprint.** `batchBaseConfig` resizes the current base with `resized` and runs it through `synchronizeWorkspace`, the same path as typing that size, so per-footprint magnet overrides and automatic counts apply; the current footprint exports the current config untouched. Every entry builds through `buildMesh` with `exportSegmentsFor`, like a single export. Batch 3MFs keep one object per size and place each copy as an instance, shelf-packed by `packPlates` onto as many build plates as it takes without overlap.
- **3MF projects always target a two-nozzle Bambu Lab X2D and must name it.** There is no printer option: anyone on another printer changes it in Bambu Studio. A part takes its filament from the `extruder` metadata of its `<part>` in `model_settings.config`, matched by the component's `objectid`, and `filament_map` puts the body on one nozzle and the other colours on the second. That nozzle cannot reach the first 20.5mm of the plate, so `packPlates` starts inside it. Colours come from `workspace.filaments`, one set of Bambu PLA Basic colours saved with the workspace, picked from swatches in the page header because they belong to no one generator, and used by every generator's preview and 3MF, never by share links. The header shows as many swatches as the part on screen has colours, read from the preview mesh. `needsBrim` gives an object a brim when it stands tall for what touches the plate, its height over the square root of its contact area: on real prints a counter's side pieces held at 0.26 and its dials at 0.40 and tube snapped off. Bambu Studio checks `printer_model` against its vendor profiles, then `nozzle_diameter` against the extruder settings; a project that passes neither loads as geometry only with "The 3mf file has invalid config". Bambu Studio's command line crashes slicing these minimal projects, `main`'s included, so check them in the app.
- **`makerworld/*.scad` are hand ports of the generators for MakerWorld's Parametric Model Maker**, which runs OpenSCAD and gives a listing a Customize button. Change a script with the geometry it ports, then run `just makerworld check <name>`: it renders that script's cases and fails on more than 0.2% symmetric-difference volume against the app or any open edge after welding. A listing runs the copy uploaded to it, not the repo's, so a changed script also replaces the `.scad` under the listing's Raw Model Files, which `makerworld` in `src/lib/pages.ts` links. It needs an OpenSCAD snapshot with Manifold (`brew install --cask openscad@snapshot`); stable 2021.01 is too old. Each script is one file because PMM cannot follow local includes, and each is licensed CC BY-SA 4.0 rather than AGPL, because MakerWorld offers only Creative Commons or its own licence. PMM has no list inputs or image uploads, so the holder takes one miniature group, the paint rack one straight module with optional ends, and tokens text only. Standard sizes, glyph metrics and glyph outlines are generated into each script from `presets.ts` and the bundled Oswald, named on its `// <generated by scripts/makerworld.ts: …>` marker. PMM's OpenSCAD may lack `textmetrics`, and `text()` kerns and hints, moving glyph points by tenths of a font unit at any size; that is lost in a base's label but misses parity wherever text is most of a part, so token text and counter digits are drawn from the generated outlines. Label fitting in `base.scad` finds the app's chosen 0.25mm sample from intervals instead of testing each one, which took 95s on a 160mm base; both the wall margin and each obstacle's clearance are convex along a ray, so each blocks one interval. `holder.scad` repeats the app's packing bit for bit, random relaxation included, relying on `Math.hypot` matching `sqrt`; changing `relaxedPacking`'s seeds, iteration counts or limits means changing the script. Ports size curves the way the app's export does, from the whole part, so a paint-rack piece takes its segments from the whole loadout's.
- **Worker meshes must be copied before transfer.** `getMesh()` may hand back arrays viewing WASM memory, and transferring that buffer would detach the heap.
- Flat shading in the preview is deliberate: Manifold shares vertices across hard edges, so averaged normals round off the wall and flatten the embossed number.

## UI

- **Global settings used by multiple generators are workspace settings.** Their canonical values live in `WorkspaceState.shared`, and `synchronizeWorkspace` projects them into the base, holder and painting-tray geometry configs. The complete workspace is persisted in browser storage. Never add matching values that write each config independently. Base label visibility and holder size engraving are the same preference, so both panels name the toggle "Labels"; magnet dimensions, per-footprint count overrides, pocket-pattern version, wall thickness and magnet boss wall are also shared. Pattern version 1 preserves the legacy five-pocket cross; balanced saved counts migrate to version 2 overrides. Similar names do not imply shared geometry: base height, holder height, and painting-tray thickness describe different printed parts. Holder shape and size belong to each miniature group, while painting-tray rows, columns, and spacing are independent.
- **Resets take their defaults from `defaultWorkspace()`**, the same source the loader falls back to, so they cannot drift. `resetGenerator` replaces one generator's config and never touches `shared`; resetting the base also empties `batch`, which is a list of base footprints; `resetShared` is a separate action because folding it into the base reset would silently change holders and spray trays too.
- **Share links are untrusted saved state.** `applyWorkspaceSetup` runs a link through the same migrations and `isWorkspaceState` validation as `loadWorkspace`; never apply a decoded hash any other way. A link carries `WORKSPACE_VERSION`, so the workspace migrations already upgrade old links and a workspace version bump needs nothing extra here; `SHARE_VERSION` changes only when the link envelope itself does. Links for every generator that reads `shared` (bases, holders, spray trays) carry it, with count overrides limited to that part's own footprints so applying one leaves the recipient's other overrides alone. A base link never carries `batch`: that is the sender's export queue, not part of the design being shared. `main.tsx` takes the hash out of the address before analytics starts, so a shared setup never reaches a captured URL.
- Components come from shadcn's Base UI registry (`components.json`, style `base-nova`). Add them with `pnpm dlx shadcn@latest add <name>`; treat `src/components/ui/**` as vendored and never hand-patch it — a handful of lint rules are switched off for that folder instead, so re-adding a component is always safe. Anything vendored but unused is deleted; re-add it when it is needed.
- **Reach for a registry component before writing one.** `src/components/controls.tsx` holds only the app-specific compositions — `Section`, `Dimension`, `PictureChoice`, `CompactChoice`, `ToggleSetting` and `SizeSelect` — and each is a thin wrapper over `Field`, `InputGroup`, `Select`, `RadioGroup` or `Switch`. Every one of those started life hand-rolled, and the hand-rolled versions were the parts that lacked keyboard support.
- **A choice whose options look different is a picture grid.** `PictureChoice` shows each option as a small drawing over its name, so what it does is clear before it is picked; a `Select` is left only for lists too long to lay out, such as standard sizes, and for the compact per-group shape inside a list of groups. The drawings live in `src/components/pictures.tsx`, 40×30 in `currentColor`: the body faint, edges solid, anything in the second colour filled. Texture and edge-profile pictures are drawn from the generators' own `textureCells`, `reliefSample` and `profileSteps`, so a picture cannot drift from the model; relief textures are lit on a canvas and used as a mask so they still take the theme's colour. Keep labels short enough for two lines at four across.
- **Fine-tuning hides behind Advanced settings, but never a change.** `Dimension`, `PictureChoice` and `ToggleSetting` take `advanced`; such a control hides while it is at its `defaultValue` (or follows the size) and the Advanced toggle (`AdvancedToggle`, at the bottom left of the canvas beside a docked panel, or in the drawer's header) is off, and shows the moment it differs, so nothing shaping the model is ever out of sight. That makes a `defaultValue` mandatory on every advanced control, or it could never reappear. A `Section` with nothing left to show hides itself through `not-has-[[data-slot=field],button]`. The toggle's state lives in `src/lib/advanced.tsx`, remembered per browser rather than saved in the workspace, because it is how someone likes the panel and not part of a design; outside its provider every setting shows. End-to-end specs start with it on, and one spec checks the hiding.
- **The semantic token mapping lives in `src/styles.css`, not in the `shadcn/tailwind.css` import**, which only carries keyframes. Without the `@theme inline` block mapping `--color-background: var(--background)` and friends, utilities like `bg-background` and `border-border` are simply never generated and the app renders unstyled. After touching the theme, check the built CSS actually contains them rather than trusting the page to look right in dev.
- Use the semantic token that means the thing rather than an opacity on a neighbouring one — `text-muted-foreground`, not `text-foreground/85`. `note`, `readout` and `sheet` are `@utility` rules, so they compose with variants like any other utility; do not add plain global classes.
- **Values that come from data go through a style, not a class name.** Tailwind's scanner only sees literal class names, so dynamic layouts set values like `gridTemplateColumns` inline rather than interpolating `grid-cols-${n}`.
- Use Tailwind's spacing scale for fixed layout dimensions when a nearby step fits; reserve arbitrary values for dimensions the scale cannot express.
- `PictureChoice` and `CompactChoice` serialise through their options list so numeric values survive the string APIs underneath. Their `label` is required because a grid of pictures or a compact trigger may have no other accessible name.
- **The worker answers exactly one kind of question.** `WorkerRequest` is a config and an id, with no discriminator: it always builds one mesh. `useGenerator` owns the persistent preview worker, while `buildMesh` starts a one-shot worker for a high-quality export, so export resolver bookkeeping never leaks into preview scheduling.
- **The settings panel is one instance, docked or drawered.** Above `md` it stands beside the viewport; below it slides in from the left as a `Sheet`. `useMediaQuery` picks which, rather than rendering both and hiding one with CSS — two copies would duplicate every control's id and every label, and Playwright would find two of everything.
- **A phone gets a tidy view, not a reduced one.** People pick a model on their phone and send the 3MF straight to Bambu Handy. Below `xl` the generators' full names no longer fit beside the name, colours and downloads, so they drop to a full-width row of their own; scrolling them sideways instead slid them under the name on tablets. Below `sm` they take their short names, tightened until all seven fit at 360px, and the top row holds the settings button, the name (hidden under 22rem), the colours, and the downloads, STL as an icon and 3MF named since that is what goes to Bambu Handy. The swatches overlap in a space kept for three, so the header holds its height on every page, and each picker opens centred under its swatch. The title block shrinks to its name and status in a strip along the foot, Explode moves to the top left so it is not covered, and Advanced moves into the drawer's header beside the settings it shows, since the canvas is hidden while the drawer is open. End-to-end specs check a 360px screen has no sideways scroll with every generator and the 3MF button in view, that a third colour leaves the header's height alone, and that on a tablet every generator sits clear of the name.
- **Standard sizes are chips under the typed dimensions, not a mode.** The diameter, or width and depth, are always there to type, and `StandardSizes` lights up the chip they match, with what that size is for in a caption two lines tall so moving between sizes never shifts the panel. There is no custom mode to enter: a typed size and the same standard size are one state. A footprint has no reset or highlight of its own, because it is a choice rather than a departure from a default. Holder groups keep a compact `SizeSelect` because each row has no room for chips.
- **Nothing is said twice.** The title block carries only what the leaders and the controls do not — no footprint, no height. Explanatory captions are reserved for states that controls alone cannot make clear.
- **Dimensions are typed, not dragged.** `Dimension` is an `InputGroup` around a number input with drag-to-scrub on its label, because a slider cannot land on 28.5. Its scrub listeners are attached in the pointerdown handler: setting a ref does not re-render, so an effect would never observe the drag starting — that bug made scrubbing silently do nothing.
- The theme is a workshop print: graphite sheet, chalk lettering, red for anything that measures or is selected, copper reserved for magnets, and amber for a setting moved off its default so it never reads as the red. Colours are `oklch()`, the way shadcn writes them. There is no light mode and no `dark` class — the tokens in `:root` are the theme, and the 3D scene reads the same ones through `themeColor()`.
- **The drawing conceits are load-bearing, not decoration.** Panel headings number themselves off a CSS counter reset on the panel — a counter rather than a prop so the numbering cannot drift out of step with the order sections actually render in. The viewport carries registration marks at all four corners, and the title block sits in the trim at `inset-5`.

## Preview behaviour

- **No debounce.** A preview starts the moment the worker is free, and while it is busy only the newest config is held. A trailing debounce meant nothing rendered at all until a drag finished. Typical previews are ~15ms, so a twenty-step drag renders nineteen distinct meshes.
- **Nothing reports a pending preview.** At ~15ms a spinner strobes on every drag step without ever telling anyone anything, so the title block says only `ready` or `blocked` and `useGenerator` exposes no busy flag. Export buttons do disable themselves while their separate high-quality build runs.
- **The scene's colours go through a one-pixel canvas.** three.js parses nothing past sRGB and merely _warns_ on an oklch token before falling back, so the theme silently stops reaching the 3D view. `themeColor()` paints the token and reads the pixel; check the console for `THREE.Color: Unknown color model` after touching the palette.
- **The key light sits ~38° off vertical, on nearly the default camera's bearing, and it casts shadows.** Everything worth seeing here is a shallow step off a flat floor — the size label is 0.6mm — so from a plan view the emboss and the floor beneath it share a normal and shade identically: with overhead lighting the number simply vanished. Any off-vertical light replaces that with a cast shadow, which reads from any angle. Lower is not better: at 26° the well wall threw its shadow halfway across a small base for no gain in legibility. A key from the front left, about 70° round from the camera, left whole faces of a tall paint rack near black. The shadow frustum is fitted to the part on every geometry swap, so a 25mm base gets the same texel density as a 180mm one.
- **The scene renders on demand.** The animation loop advances `controls.update()` every frame but draws only when a frame is marked dirty: by the controls' `change` event, a resize, a geometry swap or a view switch. Drawing an unchanged scene every frame kept the main thread fully busy for as long as the page was open, which starved input and slowed every e2e action whenever the machine was loaded. Anything new that changes what is on screen must mark the frame dirty.
- **The shadow map is drawn once per geometry swap, not per frame.** `shadowMap.autoUpdate` is off and `needsUpdate` is set alongside the mesh, because only the camera moves. Leaving it on cost 13fps against 121.
- **The camera never moves as the base resizes**, so a 180 really is seven times a 25 on screen. An earlier version pulled back to keep large parts framed, which cancelled the growth exactly: past 120mm the distance scaled with the part and nothing appeared to change. Bases past about 100mm run off the frame, which is deliberate — scrolling out is the viewer's call.
- **Each generator owns its camera view.** Switching generators saves that page's orbit and zoom, then restores the destination page's last view or its own initial framing. Never carry one generator's camera straight into another: a useful close view of a base can put an entire holder or spray tray off-screen. Damping momentum counts as camera state: the switch lands it in the view being left before saving, otherwise a drag still coasting rotates the destination's view.
- **The spray-tray camera orbits around the handle axis, not the tray or an assumed positive-Z bounding box.** Its assembled handle extends below `z = 0`, so the target follows the handle centreline at half its length, including lean and pistol-grip curvature. Its dimension leaders likewise use the assembly's real negative `minZ` and tray-top `maxZ`.
- **Framing fits the narrower axis, and only until the viewer takes the camera.** The field of view is vertical, so fitting on height alone put a 60mm base at twice the width of an upright phone. `framingDistance` divides by the smaller of the two half-extents. It is reapplied on viewport resize while `held` is false, and `held` flips on the first `start` event from the controls — after that a window resize or a rotating phone leaves the view exactly where it was put.
- **Rotation is an orbit with the up axis pinned, and the polar angle left unclamped.** `TrackballControls` was tried so the same axis could roll over and over, but tumbling with no fixed horizon made it hard to tell which way up the part was, so it went back. Unclamped means dragging one way reaches a plan view of the recess and dragging the other passes the horizon to the face the model stands on, each stopping at its pole rather than carrying on over the top. Do not restore `maxPolarAngle = Math.PI / 2`: both faces are worth seeing.
- **Explode is a view, not a setting.** The spray tray and the dial counter, whose previews assemble parts that print apart, show an Explode toggle in the viewport. It passes `exploded` to the preview config only, so it is never saved, shared or exported, and it hides the dimension leaders, which measure the assembled part. The viewer frames the exploded extents instead, from `counterLayout` with `exploded` and `paintingTrayExplodedFrame`, so toggling refits the camera like any other geometry swap until the viewer has taken it. The counter moves each wheel a barrel's width and more along the axle, and lifts every tile out of its pocket; `counter.test.ts` runs the exploded views through the same no-contact volume check as the assembly. The spray tray stands its grip off the tray's front edge, because dropped straight down it hides under the tray from the default camera.
- **A weak upward bounce light exists only so the underside is not black**, since the sky-to-ground hemisphere leaves downward faces nearly unlit.

## Testing notes

- E2E waits on the triangle count changing, not on the status reading "ready" — that is still true from the previous build and makes assertions race. The count comes from `data-triangles`, which the viewport stamps on its host from the mesh it has actually installed in the scene.
- **Watertightness is asserted against a real export, never in the app.** A `stats.solid` badge used to claim it in the title block while only testing that the mesh was non-empty; it stayed lit right through the rib/wall tangency bug. `BaseStats` still carries triangles, volume and mass for the tests and the samples script. The only figure the UI reads is `grams`, which the worker returns with each preview so the title block's filament estimate weighs the mesh on screen. It is labelled as solid PLA because a slicer's walls and infill print lighter; preview and export weights agree to about 0.1%.
- Standard sizes are picked through the combobox named "Standard base size"; its options read `"<size> <what it is for>"`, so specs anchor a regex on the figure.
- Footprint and height are asserted on the dimension leaders (`#label-across`, `#label-height`), not the title block, which no longer repeats them.
- When changing geometry, check an actual export rather than the preview. `trimesh` welds vertices on load, which is how the tangency bug was caught.

## Deployment

Static assets only, described by `wrangler.jsonc`. Cloudflare builds the repo with `pnpm build` and serves `dist/`. There is no backend, no database and no secret — the generator, the exporters and the font all run in the browser. Manifold's WASM is the single-threaded build, so no cross-origin isolation headers are required.

- **Every generator route is a prerendered file.** The `hobbykit:seo` plugin in `vite.config.ts` writes one HTML file per entry in `src/lib/pages.ts`, each with its own head, structured data and a readable summary inside `#root` that React replaces on mount, plus `404.html`, `robots.txt`, `sitemap.xml`, `llms.txt`, and a Markdown copy of each generator's guide from `docs/generators`, linked from its page as the `text/markdown` alternate. The README links those guides rather than repeating them, and a test holds every guide's heading to its page title. `wrangler.jsonc` serves `404.html` for anything else, so a new generator needs an entry in `PAGES` or its address returns 404. Each page's link preview is a 1200×630 screenshot of its default model in `public/og`; run `just social-cards` when the app's look or a default changes, which also retakes the README screenshots. The README leaves the dial counter out until its design is changed.
- `public/_headers` sets the security headers Cloudflare sends with every asset. There is no Content-Security-Policy: PostHog's ingest host comes from the build environment and its extensions load from its own asset hosts, so a policy cannot be checked locally and a wrong one silently drops analytics.
